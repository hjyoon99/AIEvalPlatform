# 모델과 에이전트 역할

## 1. 현재 사용 모델

현재 기본 모델은 모든 역할에서 Ollama의 `qwen3.5:4b`다.

```text
Runtime: Ollama
Default model: qwen3.5:4b
Default endpoint: http://localhost:11434
```

모델 선택은 클라우드 API 비용과 키 관리 없이 로컬에서 전체 흐름을 재현하고, 4B급 모델로 개발 장비에서도 반복 평가하기 위한 방향과 맞는다. 반면 소형 로컬 모델은 긴 JSON을 반복하거나 구조화 출력을 완전히 지키지 못할 수 있으므로 코드에 파싱 실패 대비 로직이 들어 있다.

저장소에는 다른 모델을 실제 사용했다는 기록이 없다. Dashboard와 API에서 모델 이름을 전달할 수 있어 시나리오 생성과 대상 답변 생성 모델은 바꿀 수 있지만, Verifier/Evaluator/Supervisor 생성자 기본값은 현재 `qwen3.5:4b`로 고정되어 있다.

## 2. 하나의 모델, 여러 역할

같은 모델을 사용해도 시스템 프롬프트, 입력 컨텍스트, 온도와 출력 스키마를 달리해 역할을 분리한다.

| 역할 | 모델 | 온도 | 주요 출력 |
| --- | --- | ---: | --- |
| Executor | qwen3.5:4b 또는 실행 요청 모델 | 0.7 | 자유 형식 답변 |
| Verifier | qwen3.5:4b | 0.0 | `isValid`, `reason` |
| Evaluator | qwen3.5:4b | 0.0 | 지표별 점수와 근거 |
| Supervisor | qwen3.5:4b | 0.0 | PASS/FAIL/RETRY |
| Scenario Generator | 요청 모델 | 0.4 | 시나리오와 루브릭 |
| Scenario Validator | 요청 모델 | 0.0 | 유효성, 점수, 문제 목록 |

창작이 필요한 답변 생성과 시나리오 생성에는 0보다 높은 온도를 사용하고, 판정 역할에는 0.0을 사용한다. 평가 결과의 변동을 줄이기 위한 설정이다.

## 3. Executor

목적은 평가 대상 출력이 제공되지 않았을 때 테스트용 답변을 만드는 것이다.

- 기본 시스템 지시: 명확하고 친절하게 답변
- `metadata.systemPrompt`가 있으면 대상 에이전트의 시스템 지시로 대체
- `think=False`로 최종 답변만 받음
- 외부 답변이 제공되면 Executor는 호출되지 않음

Executor의 출력은 채점 결과가 아니라 평가 대상이다. 이 역할과 Judge를 분리해야 “답을 만든 모델이 자기 점수를 직접 정하는” 구조를 피할 수 있다. 다만 현재 기본 설정에서는 실제 기반 모델이 같으므로 엄격한 독립성이 필요한 실험에서는 역할별 모델을 분리해야 한다.

## 4. Verifier

Verifier는 점수를 주기 전에 평가 가능한 답변인지 거른다.

1. 빈 문자열이면 즉시 실패
2. 길이가 5자 미만이면 즉시 실패
3. 그 외에는 모델로 관련성, 오류 메시지, 유해 내용, 깨진 문자열을 확인

간단한 규칙을 먼저 적용하는 이유는 명백한 실패에 모델 호출 비용과 시간을 쓰지 않기 위해서다.

구조화 출력은 Pydantic의 `VerificationSchema`를 Ollama `format`에 전달한다. 모델 호출 자체가 실패하면 `error`를 포함한 실패 결과로 반환하며, Supervisor는 이를 품질 보장 불가로 판단한다.

## 5. Evaluator

Evaluator는 LLM-as-a-Judge 역할이다. 입력에는 다음 정보가 포함된다.

- 사용자 프롬프트
- 실제 AI 출력
- 선택적 기대 출력
- 정책 지표와 가중치
- 시나리오별 루브릭
- 필수 조건, 즉시 실패 조건, 허용 표현
- 재평가 시 Supervisor 피드백

정책이 없을 때는 사실 정확성과 답변 관련성을 각각 0.5 가중치로 사용하는 기본 지표가 적용된다.

모델이 반환해야 하는 값은 지표 key, 0~1 점수, 지표별 근거, 전체 평가 요약, 위반한 실패 조건과 누락한 필수 조건이다. 실제 최종 점수 계산은 Python 코드에서 수행한다. 모델에게 가중 합산까지 전적으로 맡기지 않아 산술 오류와 정책 불일치를 줄인다.

주의할 점은 Evaluator 내부의 `passed` 계산은 0.7을 기준으로 하지만, 최종 판정은 Supervisor가 실행별 `passThreshold`를 사용한다는 것이다. 현재 저장과 UI의 최종 기준은 Supervisor verdict다. 향후 혼동을 없애려면 Evaluator의 `passed`를 제거하거나 실행별 threshold를 전달하는 편이 좋다.

## 6. Supervisor

Supervisor는 검증과 평가 결과를 감사한다.

- Verifier 실행 오류 또는 유효성 실패는 즉시 FAIL
- Evaluator 오류이며 재시도 횟수가 남으면 RETRY
- 모델에게 원본 답변, 기대값, 검증과 평가 결과, 통과 기준을 제공
- 모델이 PASS/FAIL/RETRY, 신뢰도, 사유, 이슈와 권장 조치를 반환

Supervisor LLM이 점수 기준을 어기면 애플리케이션 규칙이 판정을 교정한다.

```text
Supervisor가 PASS 반환
AND score < passThreshold
=> 강제로 FAIL + SCORE_BELOW_PASS_THRESHOLD
```

Supervisor 호출이 실패해도 전체 결과를 잃지 않는다. 점수가 기준 이상이면 PASS, 아니면 FAIL로 결정하고 신뢰도 0.5와 오류 내용을 남긴다. 이는 “설명 에이전트 실패”와 “평가 데이터 전체 실패”를 분리한 폴백이다.

## 7. Scenario Generator와 Validator

Generator는 프로젝트 도메인, 설명, 업무 컨텍스트와 평가 정책을 받아 정상·경계·실패 상황을 섞은 테스트를 만든다.

각 시나리오는 다음을 포함한다.

- 제목, 카테고리, 프롬프트
- 기대 출력과 기대 행동
- 위험 수준
- 지표별 1.0/0.75/0.5/0.25/0.0 루브릭
- 필수 조건
- 즉시 실패 조건
- 허용 가능한 의미상 변형

같은 호출에서 생성과 검증을 한 번에 맡기지 않고, 생성 후 별도 Validator 호출을 한다. 생성 모델의 자기 확신을 그대로 승인 상태로 쓰지 않고 평가 가능성, 현실성, 도메인 관련성을 다시 확인하기 위해서다.

구조화 검증 응답이 잘리거나 파싱되지 않으면 생성 결과를 삭제하지 않는다. 대신 점수 0, `DRAFT`, `VALIDATION_RESPONSE_ERROR`로 내려 사람이 검토할 수 있게 한다. 자동화 실패를 데이터 손실로 연결하지 않는 설계다.

## 8. 모델 교체 시 확인할 사항

1. Ollama에 모델이 설치되어 있는가?
2. Pydantic JSON Schema 기반 structured output을 안정적으로 따르는가?
3. 한국어 평가 근거 품질이 충분한가?
4. 루브릭이 길어졌을 때 context window가 충분한가?
5. 0.0 온도에서도 결과 편차가 허용 범위인가?
6. Judge와 Target 모델이 같을 때 발생하는 자기 선호 편향을 허용할 것인가?

운영 수준에서는 Generator, Target, Verifier, Judge, Supervisor 모델 이름과 프롬프트 버전을 EvalRun에 함께 저장해야 같은 평가를 재현할 수 있다.
