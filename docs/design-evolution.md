# 설계 변화와 구현 이야기

## 1. 기록을 읽는 방법

이 문서는 Git 이력과 현재 구현에서 확인할 수 있는 변화 순서를 이야기 형태로 정리한다. 별도의 당시 회의록이 없으므로 “왜”에 대한 일부 설명은 코드에 남은 제약과 결과에서 역추적한 판단이다.

## 2. 1단계: 먼저 뼈대를 세우다

초기 저장소에는 NestJS, Prisma와 디렉터리 골격이 먼저 만들어졌다. `apps/backend`, `apps/agent-engine`, `packages/sdk`가 있었지만 평가 서비스와 Python 파일 다수는 비어 있었다.

이 단계의 의미는 구현보다 경계를 먼저 잡았다는 데 있다.

- 백엔드: 저장과 외부 API
- 에이전트 엔진: 모델 기반 평가
- SDK: 향후 공통 계약

처음부터 완성된 마이크로서비스였던 것은 아니다. 비어 있는 파일과 `evalustor.py` 같은 오탈자 파일도 있었다. 이후 평가 엔진 구현 커밋에서 올바른 `evaluator.py`와 `app/main.py`로 정리됐다.

## 3. 2단계: 단일 점수가 아니라 역할을 나누다

가장 단순한 평가는 하나의 Judge에게 “이 답변을 0~1로 평가해줘”라고 묻는 방식이다. 그러나 이 방식은 다음 실패를 구분하지 못한다.

- 답변 자체가 비어 있거나 깨짐
- 답변은 유효하지만 사실성이 낮음
- Judge의 점수와 설명이 충돌함
- Judge 호출 자체가 실패함

그래서 평가 책임이 세 단계로 나뉘었다.

1. Verifier: 애초에 평가 가능한 답변인가?
2. Evaluator: 기준별 점수와 근거는 무엇인가?
3. Supervisor: 결과가 일관되고 정책 기준을 만족하는가?

여기에 답변이 없는 테스트를 위해 Executor가 추가됐다. 구조는 “여러 에이전트가 자유롭게 토론”하는 형태보다 품질 게이트가 순서대로 배치된 파이프라인에 가깝다.

## 4. 3단계: 직렬 호출에서 상태 그래프로

세 함수를 차례로 호출하는 것만으로도 첫 버전은 만들 수 있다. 하지만 재평가가 들어오면 문제가 생긴다.

- 어느 결과를 유지하고 어느 결과를 덮어쓸 것인가?
- 재평가 피드백은 어디에 저장할 것인가?
- 최대 횟수는 어느 단계에서 검사할 것인가?
- 종료 조건을 if 문 여러 곳에 둘 것인가?

LangGraph의 `EvaluationState`와 조건부 간선을 사용하면서 이 제어 흐름이 하나의 그래프로 모였다. Supervisor가 RETRY를 반환하면 Evaluator로 돌아가고, 그 외에는 종료한다.

중요한 설계 변화는 재시도가 “답변 재생성”이 아니라 “평가 재검토”라는 점이다. 원본 답변을 바꾸면 같은 대상을 재평가하는 것이 아니기 때문이다. 현재 그래프는 Supervisor 사유를 Evaluator에 전달해 동일 출력의 채점을 다시 검토한다.

## 5. 4단계: 데이터셋 실행에서 프로젝트 중심으로

초기 평가 API는 이름, 에이전트, 모델과 dataset을 받으면 충분했다. 그러나 실제 사용 흐름에서는 매번 JSON을 직접 만드는 방식이 오래 유지되기 어렵다.

그래서 데이터 모델이 다음 방향으로 확장됐다.

```text
Project
├── EvaluationPolicy
├── Scenario
└── EvalRun
    └── EvalResult
```

Project는 도메인과 업무 맥락을 제공한다. Policy는 지표, 가중치, 통과 기준을 관리한다. Scenario는 재사용 가능한 테스트 자산이 된다. EvalRun은 특정 시점의 실행이고 EvalResult는 개별 항목 결과다.

이 변화로 “평가 한 번 실행”이 “조직이 반복해서 관리하는 평가 체계”로 바뀌었다.

## 6. 5단계: 고정 지표에서 동적 정책과 루브릭으로

처음 생각하기 쉬운 지표는 정확성과 관련성 두 가지다. 실제 도메인에서는 평가 기준이 달라진다.

- 고객 상담: 정책 준수, 공감 표현, 금지 약속
- 의료 안내: 안전 고지, 진단 단정 금지
- 사내 검색: 근거 충실성, 문서 범위 준수

따라서 EvaluationPolicy의 metrics를 JSON으로 저장하고, weight의 합만 Backend에서 검증한다. 시나리오에는 정책 지표별 세부 점수 구간과 필수·실패·허용 조건을 넣었다.

이 과정에서 루브릭 형식이 한 번에 고정되지 않았던 흔적도 있다. `normalizeRubric`은 이미 `metrics` 배열인 새 형식뿐 아니라 지표 key 아래에 level 배열이 있는 이전 형식도 현재 구조로 변환한다. 데이터가 발전하는 동안 기존 생성 결과를 버리지 않기 위한 호환 계층이다.

## 7. 6단계: 자동 생성만으로는 부족했다

시나리오를 LLM이 생성하면 생산 속도는 빨라진다. 하지만 잘못된 기대 답변이나 평가 불가능한 테스트가 들어가면 이후 점수 전체가 무의미해진다.

그래서 두 개의 안전장치가 들어갔다.

1. 별도 자동 Validator가 도메인 관련성, 명확성, 일관성, 현실성, 평가 가능성을 확인
2. 최종적으로 사람이 APPROVED해야 실행 가능

`AUTO_VERIFIED`와 `APPROVED`를 분리한 것이 핵심이다. 자동 검증 통과는 추천 신호이고, 실제 평가 자산 편입은 사람의 결정이다.

또한 승인 후 내용을 수정하면 다시 DRAFT가 된다. 검토한 버전과 실행할 버전이 달라지는 문제를 방지한다.

## 8. 7단계: 모델 판단 위에 결정 규칙을 두다

LLM Supervisor에게 최종 판단을 맡기면 자연스러운 설명을 얻을 수 있지만, 사용자가 0.8을 통과 기준으로 정했는데 0.6을 PASS로 판정할 가능성을 완전히 없앨 수 없다.

현재 구현은 두 층으로 해결한다.

- LLM: 맥락과 상충 관계를 종합하고 설명 생성
- 코드: 점수 미달 PASS 금지, 재시도 횟수 제한

이것은 LLM을 제거하는 것이 아니라 LLM이 잘하는 정성 판단과 프로그램이 잘하는 불변 조건을 분리한 것이다.

## 9. 8단계: 관찰 가능한 결과로 확장

최종 점수만 저장하면 낮은 점수의 원인을 알 수 없다. EvalResult에는 다음을 분리해 저장한다.

- verification
- evaluation
- supervision
- retryCount
- durationMs
- reason

Dashboard는 이 정보를 이용해 결과뿐 아니라 판단 경로를 보여준다. 이 단계에서 플랫폼의 목표가 단순 채점보다 “왜 이런 결과가 나왔는지 설명하는 평가 운영 도구”로 확장됐다.

## 10. 9단계: 근거 충실성 검증을 도입하며 내린 두 가지 결정

`classify_answer_type`이 RAG 유형 답변을 `groundedness_check`로 분기하도록 만든 뒤(#19), 실제 `GroundednessAgent`(#20)를 설계하며 스키마 두 곳에서 선택지가 갈렸다. 둘 다 나중에 바꾸면 호출부와 프롬프트를 동시에 고쳐야 하는 지점이라 결정과 근거를 남긴다.

**1) `unsupportedClaims`를 문자열 목록이 아니라 `{claim, reason}` 객체 목록으로 정의했다.**

근거 문서로 뒷받침되지 않는 주장에는 성격이 다른 두 경우가 섞여 있다: 문서에 아예 언급이 없는 경우와, 문서 내용과 실제로 모순되는 경우(더 심각하다). 주장 문자열만 반환하면 이 둘을 구분할 수 없어 결과를 보는 사람이 심각도를 판단하기 어렵다. `reason`을 함께 반환하면 "언급 없음"과 "모순됨"을 LLM이 바로 구분해 알려줄 수 있다. 이는 `VerifierAgent`/`EvaluatorAgent`/`SupervisorAgent`가 모든 판정에 `reason`을 동반하는 기존 관례와도 일치한다.

**2) `output_metadata.retrievedDocuments`의 항목 형식을 문자열과 `{content, source?}` 객체 둘 다 허용하도록 했다.**

SDK의 `ExecutionResult.metadata.retrievedDocuments`는 애초에 `unknown[]`로 느슨하게 정의되어 있다(#18) — 답변 유형 분류가 되는 최소 조건(필드가 "있다/없다")만 계약으로 확정하고, 내부 구조는 고객사 RAG 구현마다 다를 수 있다는 전제였다. 여기서 하나의 엄격한 객체 스키마를 강제하면 그 설계와 어긋난다. 출처 추적을 하지 않는 단순한 RAG는 문자열 배열을 그대로 보내면 되고, 출처(URL, 문서 ID 등)를 추적하는 RAG는 `{content, source}`로 보내 나중에 "왜 이 주장이 근거 없다고 판단됐는지" 사람이 원본까지 추적할 수 있게 한다. `GroundednessAgent`는 프롬프트를 구성할 때 두 형태를 모두 정규화해서 받아들인다.

## 11. 10단계: 도구 호출 검증에서 "정답 스키마 없음"을 받아들이다

`tool_call_check`(#21)를 설계할 때 `groundedness_check`와 똑같은 질문이 다시 나왔다: 무엇을 기준으로 "정확하다"고 판단할 것인가. `groundedness_check`는 `retrievedDocuments`라는 명확한 대조 대상이 있었지만, 도구 호출에는 그런 게 없다 — "이 프로젝트에서 쓸 수 있는 도구 목록과 파라미터 스키마"라는 메타데이터 자체가 계약에 없기 때문이다.

이슈 자체도 "파라미터 정확성/순서/불필요한 호출 여부 중 결정"이라고 열어뒀다. 세 후보를 검토했다.

- **파라미터 정확성**: 스키마가 없으니 타입 수준 검증은 불가능하다. 대신 "사용자 질문 의도에 비춰 파라미터가 명백히 부적절한가"라는 의미적 판단은 LLM이 prompt 하나만 보고도 할 수 있다(예: "서울 날씨"를 물었는데 도쿄로 조회).
- **불필요한 호출**: 마찬가지로 prompt만 보고 "이 호출이 질문에 답하는 데 애초에 필요했는가"를 판단할 수 있어, 추가 메타데이터 없이 같은 스키마에 묶을 수 있었다.
- **호출 순서**: "올바른 순서"를 판단하려면 의도된 실행 계획을 알아야 하는데, 그런 정보가 계약에 없어 지금은 판단 근거가 없다. 그래서 이번 범위에서 제외했다.

즉 groundedness와 마찬가지로, 도구 호출의 "정답"을 미리 아는 게 아니라 LLM이 prompt 문맥만으로 합리적으로 판단할 수 있는 항목만 검증 대상으로 삼았다. `toolCalls` 항목 형식도 `retrievedDocuments`와 같은 이유로 `{name, arguments}`를 가정하되 문자열이나 다른 필드명도 관대하게 받아들이도록 했다 — SDK 계약이 `unknown[]`로 느슨하게 정의되어 있는 건 마찬가지이기 때문이다.

## 12. 11단계: 새 큐를 들이지 않고 기존 큐의 동시성만 확장하다

Judge 처리량을 늘려야 하는 시점에 두 방향이 있었다: Redis + BullMQ 같은 별도 메시지 큐를 새로 들이는 것과, 이미 있는 `JudgeJob`(Postgres 기반 lease/claim 큐)을 그대로 두고 폴링 루프만 여러 개로 늘리는 것.

**[Problem]** `JudgeWorkerRepository`는 이미 `JudgeJob` 테이블로 큐잉이 되어 있었지만, 폴링 루프 자체가 단일 타이머 하나였다. `claim()` → `process()`를 완료해야 다음 `tick()`이 돌아서, `PENDING` 작업이 몇 개 쌓여 있든 항상 하나씩만 처리됐다. 시나리오 여러 개를 한 번에 넣으면 케이스 수만큼 순차적으로 대기 시간이 늘어났다.

**[Why]** `claim()`은 이미 `updateMany({ where: { id, status: 'PENDING' } })`라는 조건부 원자적 갱신으로 선점하고 있었다 — 이건 여러 워커가 동시에 같은 작업을 노려도 안전하게 하나만 이기도록 설계된 패턴이다. 즉 동시성을 위한 안전장치는 이미 있었고, 실제로 동시에 도는 폴링 루프가 하나뿐이었을 뿐이다. 여기에 Redis/BullMQ를 얹으면 같은 문제(안전한 동시 선점)를 이미 풀어둔 걸 다시 푸는 셈이고, 새 인프라 의존성만 늘어난다. 반대로 이미 검증된 lease/claim 로직을 재사용하면 위험 없이 처리량을 늘릴 수 있다고 판단했다.

**[How]** 폴링 루프를 슬롯 N개(`JUDGE_WORKER_CONCURRENCY`, 기본 4)로 나눠 각각 독립적으로 `claim()`/`process()`를 반복하게 했다. `claim()`/`process()` 자체는 코드 한 줄도 바꾸지 않았다 — 이미 동시 호출에 안전하게 짜여 있었기 때문이다. 다만 슬롯 하나당 Agent Engine 호출 1건이 나가고 그 안에서 Ollama가 여러 번 순차 호출되므로, 무작정 늘리면 로컬 Ollama가 못 버틴다는 트레이드오프를 문서에 남기고 기본값을 보수적으로 잡았다.

진행 상태를 폴링 없이 받을 수 있도록 SSE 엔드포인트도 같이 추가했는데, 여기서도 같은 원칙을 적용했다. 지금은 워커와 API가 같은 프로세스 안에 있으므로 새 브로커 없이 `node:events`의 `EventEmitter`로 충분했다. 다만 이건 "지금 상태에 맞는 최소 해"이지 최종 해가 아니라는 것도 코드 주석에 남겼다 — Judge Worker가 나중에 별도 프로세스로 독립 배포되면(README의 기존 한계 항목) 이 프로세스 내 이벤트로는 부족해지고 Postgres LISTEN/NOTIFY나 Redis pub/sub으로 바꿔야 한다.

## 13. 현재 선택의 한계와 다음 변화

### 워커의 수평 확장

`JudgeJob` 큐, N-way 동시 폴링(`JUDGE_WORKER_CONCURRENCY`), SSE 진행률 스트리밍까지는 갖췄지만(11단계), 워커가 여전히 Backend API 서버와 같은 프로세스 안에서만 돈다. 프로세스 하나의 동시성 한도를 넘어서려면 Judge Worker를 별도 서비스로 독립 배포하고 여러 인스턴스로 수평 확장할 수 있어야 하는데, 그러려면 지금 프로세스 내 `EventEmitter`로 구현한 SSE 브로드캐스트도 Postgres LISTEN/NOTIFY나 Redis pub/sub 같은 프로세스 간 방식으로 바꿔야 한다.

### 모델 버전 재현성

EvalRun에는 모델 문자열과 정책 스냅샷이 있지만 역할별 모델, 실제 Ollama digest, 프롬프트 버전은 없다. 엄격한 재현성을 위해 `evaluationConfigSnapshot` 같은 구조가 필요하다.

### 공통 계약

TypeScript와 Python이 응답 인터페이스를 각각 정의한다. `packages/sdk` 또는 OpenAPI 생성으로 계약을 공유하면 필드 불일치 위험을 줄일 수 있다.

### 평가 신뢰도

단일 Judge 점수에는 편향과 분산이 있다. 다음 단계에서는 서로 다른 모델의 다중 Judge, 반복 평가의 평균·분산, golden dataset 기반 Judge calibration을 고려할 수 있다.

### 인증과 격리

현재는 로컬 단일 사용자 흐름이다. 다중 사용자 운영을 위해 인증, 프로젝트 권한, 감사 로그와 비밀 관리가 필요하다.
